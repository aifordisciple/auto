# Autonome Studio 商业级身份验证系统架构白皮书 (终极优化版)

## 一、 功能蓝图全景 (Functional Blueprint)

本架构采用 **Defense-in-Depth (深度防御)** 策略，将身份认证（AuthN）与授权（AuthZ）解耦，确保存储安全性与业务灵活性的高度统一。

### 1. 访问层 (Access Layer: Unified Portal)
提供多维度接入能力，平衡用户体验与合规性。
* **免密即触达 (Zero-friction)**：手机号 + OTP 免密登录。通过“预注册检测”实现静默注册，极大提升转化率。
* **密码登录 (Fallback)**：为已设置密码的老用户提供传统的手机号+密码登录方式。
* **专业社区集成 (Ecosystem Linking)**：
    * **GitHub OAuth**：深度绑定生信开发者的代码资产。
    * **微信/企业微信**：适配国内科研院所与企业团队的协作生态。
* **企业级单点登录 (Enterprise SSO)**：预留 **SAML 2.0 / OIDC** 接口，支持大型医疗机构或高校实验室的统一身份认证对接。
* **备用安全通道 (Recovery Channel)**：支持通过绑定的安全邮箱接收验证码或 Magic Link 找回密码，防止手机号挂失、销号导致账号资产彻底丢失。

### 2. 安全网关层 (Security & Risk Engine)
在流量触达业务核心前，进行多层风险过滤。
* **动态风控感知 (Adaptive Defense)**：集成 **Cloudflare Turnstile** 或极验验证，结合 **设备指纹 (Device Fingerprinting)** 识别机器行为。
* **多维限流策略 (Granular Rate-Limiting)**：
    * 针对手机号、IP、User-Agent 实施 Redis 分布式限流，从物理层阻断短信轰炸（SMS Flooding）和邮件轰炸。
* **爆破熔断与惩罚 (Circuit Breaker)**：实施指数级退避算法（Exponential Backoff）。连续尝试失败将锁定账号并触发报警邮件。

### 3. 核心业务层 (Core IAM: Identity Orchestration)
处理复杂的身份映射与个人敏感信息（PII）的安全管理。
* **统一标识符系统 (Unique Identity Identifier)**：所有登录渠道统一映射至内部唯一 UUID，支持多渠道无缝合并。
* **凭证生命周期管理 (Credential Lifecycle)**：提供完备的会话内修改密码、忘记密码重置以及安全邮箱绑定流水线，确保凭证的安全轮换与遗失恢复。
* **PII 数据加密存储**：手机号、邮箱等敏感信息在 PostgreSQL 中使用 **AES-256 透明加密** 存储，符合数据出境与隐私保护法规。
* **账号自动注册与合并 (Auto-Provision & Linking)**：
    * **手机号流**：检测到新手机号时，系统静默创建 `User` 记录。
    * **OAuth 流**：第三方账号登录后，系统必须校验其是否已关联主键（手机号）。未关联的第三方 ID 将被阻拦在“临时绑定凭证”状态，强制要求补充手机号完成合并后，才下发正式的业务 Token。
* **生物信息学用户画像 (Bio-Profile)**：在 Onboarding 阶段引导用户完善所属机构、科研领域（如：单细胞、表观遗传学），为后续的 **Agent 协同过滤推荐** 提供元数据。
* **双因素认证 (2FA/TOTP) [进阶项]**：允许高安全需求用户（如处理敏感临床数据的研究员）绑定 Authenticator 动态口令，在账号/密码校验后进行二次拦截。

### 4. 会话管理层 (Session Persistence & Lifecycle)
管理凭证的安全流转与审计闭环。
* **双 Token 强化机制 (Dual-Token Protocol)**：
    * **Short-lived Access Token**：JWT 格式，包含用户权限范围（Scopes），过期时间设定为 15-30 分钟，前端存在内存中，用于每次 API 请求鉴权。
    * **HttpOnly Refresh Token**：长生命周期（如 7 天），有状态，存储于持久化 Cookie，绑定 `SameSite=Lax` 属性，防范 CSRF 与 XSS 劫持。
* **主动吊销与审计 (Active Revocation & Audit)**：
    * **会话指纹记录**：每次颁发 Refresh Token，都会在 PostgreSQL 的 `active_sessions` 表中记录一条会话（包含 IP、User-Agent、过期时间）。
    * **多设备并发管控**：提供“单设备互踢”或“多设备共存”的策略配置。
    * **全球登出 (Global Logout)**：用户可在后台查看在线设备，支持一键清理所有或指定终端会话，即刻失效所有分发的 JWT（通过将 `session_id` 标记为 `revoked` 并加入 Redis 黑名单实现秒级撤回）。

---

### 补充建议：

1.  **关于合规性**：考虑到生信数据的敏感性，建议在注册时增加 **服务等级协议 (SLA)** 与 **隐私保护声明 (PIPL/GDPR)** 的强制勾选流程。
2.  **关于代码审计**：生成的 JWT 签名密钥（Secret Key）应存储在环境变量或 HashiCorp Vault 等专用的密钥管理服务中，严禁硬编码。
3.  **关于日志**：在会话层应记录每一次登录的详细元数据，以便在发生数据泄露时，能够通过 `active_sessions` 快速回溯受影响的范围。

## 二、 核心工作流引擎 (Core Workflows - 深度打磨版)

### 工作流 A：知乎式手机免密登录与自动注册流 (黄金转化链路)
此链路的架构目标是：**在绝对防御“短信轰炸（SMS Flooding）”的前提下，实现用户“零认知摩擦”的丝滑入站。**

1.  **预检触发 (Pre-flight Trigger)**：用户在登录页输入手机号，点击“获取验证码”。前端收集设备指纹（Device Fingerprint）及环境信息。
2.  **人机对抗 (CAPTCHA Challenge)**：前端动态判定风险，低风险静默通过，高风险唤起滑块/无感验证组件。获取由第三方（如 Turnstile）签发的 `captcha_token`。
3.  **网关鉴权 (Gateway Auth)**：前端向 `/auth/send-sms` 发起请求，Payload 包含 `phone`, `captcha_token`, `device_id`。
4.  **L1/L2 双重限流 (Dual-Layer Rate Limiting)**：
    * **L1 (设备/IP 锁)**：校验 Redis 中该 IP/设备 1 小时内请求是否超限（防分布式肉鸡）。
    * **L2 (业务锁)**：校验 Redis `sms:lock:{phone}`（60秒发信冷却）和 `sms:count:{phone}`（单日最高10次上限）。若触碰红线，立即返回 HTTP 429 (Too Many Requests)。
5.  **凭证生成与下发 (OTP Dispatch)**：
    * 生成高熵 6 位数字 OTP。
    * 将 OTP 存入 Redis `sms:code:{phone}`，TTL 设为 5 分钟。**为防爆破，同时记录错误尝试次数 `sms:err:{phone}: 0`**。
    * 任务投递至 Celery 异步队列，调用阿里云/腾讯云通信 SDK。若云服务异常，触发降级策略（如语音播报）。
6.  **校验与销毁 (Verification & Burn)**：
    * 用户提交 `phone` + `OTP` 请求登录。
    * 后端提取 Redis 中的 OTP 使用恒定时间比较（Constant-time comparison，防时序攻击）。
    * **容错分支**：若 OTP 错误，`sms:err:{phone}` 加 1。若错误超 3 次，立刻销毁该 OTP 并锁定，要求重新获取（防暴力破解）。
    * **成功分支**：比对成功后，**第一时间以原子操作（Atomic DELETE）销毁 Redis 缓存**，严防重放攻击（Replay Attack）。
7.  **身份解析与分流 (Identity Resolution Fork)**：
    * 开启数据库事务 (DB Transaction)。
    * **分支 1 (老用户)**：查到对应 `phone_number`，检查 `is_active` 状态。若账号被封禁，返回 403 Forbidden。
    * **分支 2 (新用户)**：未查到记录。执行 `INSERT INTO users`，生成 UUID，分配系统默认头像及脱敏昵称（如 `BioUser_8492`），初始化用户配置表。
8.  **会话锚定与下发 (Session Anchoring)**：
    * 生成 Access Token (JWT，15分钟)。
    * 生成高强度随机字符串作为 Refresh Token，记录入 PostgreSQL `active_sessions` 表（含当前时间、IP、设备指纹）。
    * 通过 HTTP 响应头 `Set-Cookie: refresh_token=...; HttpOnly; Secure; SameSite=Lax` 下发长效凭证。

### 工作流 B：第三方 OAuth 强制绑定流 (资产合规链路)
此链路的架构目标是：**在利用第三方生态快速获客的同时，通过“状态挂起”机制，确保业务数据库中绝对不存在缺乏实名主键（手机号）的“幽灵账号”。**

1.  **防伪造授权 (Anti-CSRF Authorization)**：用户点击 GitHub 登录，系统生成加密的 `state` 参数（防 CSRF 攻击）和 `PKCE` 校验码，重定向至 GitHub。
2.  **身份回调与解析 (Callback & Exchange)**：GitHub 携 `code` 和 `state` 回调 `/auth/github/callback`。后端校验 `state` 成功后，换取 GitHub Access Token，并拉取用户的 `github_id` 和 `email`。
3.  **映射寻址 (Mapping Lookup)**：查询 `oauth_accounts` 表，寻找该 `github_id`。
4.  **业务分流 (The Fork)**：
    * **分支 1 (已绑定)**：找到关联的 `user_id`。直接进入上述【工作流 A】的第 8 步（会话锚定与下发）。
    * **分支 2 (未绑定 - 状态挂起)**：未找到关联记录。**严禁直接创建 User**。后端生成一个特定的 `Bind_Token`（JWT 格式，包含 `github_id` 和 `github_email`，TTL 10 分钟，Scope 限制为 `bind_only`）。前端收到带 `Bind_Token` 的 401 响应。
5.  **强制收敛 (Forced Convergence)**：
    * 前端拦截路由，弹出不可关闭的“绑定手机号”安全模态框。
    * 用户输入手机号并完成发送验证码流程（复用工作流 A的 1-6 步）。
    * 提交时，前端向 `/auth/bind-phone` 发送 `phone`, `OTP`, 和 `Bind_Token`。
6.  **合并决断 (Merge Resolution)**：
    * 后端校验 OTP 成功，且解析 `Bind_Token` 确认合法。
    * 查询该手机号对应的 User。
    * **子分支 2a (手机号已存在 User)**：检查该 User 是否已绑定了*其他*的 GitHub 账号。若已绑定，提示冲突或提供“覆盖绑定”选项；若未绑定，将当前 `github_id` 插入 `oauth_accounts` 并关联至该 User。
    * **子分支 2b (手机号是新号)**：创建全新 User，插入 `oauth_accounts` 关联记录。
7.  **会话锚定**：下发正式 Access Token 与 Refresh Token，至此该 GitHub 身份彻底收编入主体系。

### 工作流 C：密码登录与动态风控流 (防御底座链路)
此链路的架构目标是：**为老用户保留传统登录习惯，并通过自适应风控（Adaptive Risk Control）阻断撞库与字典攻击。**

1.  **提交凭证**：用户提交 `phone` + `password`。
2.  **风控探针 (Risk Probe)**：后端在查询数据库前，先查询 Redis `login:fail:{phone}` 和 `login:fail:{ip}`。
    * 若失败次数 >= 5 次：立即返回 429 锁定状态，提示“账号尝试次数过多，已锁定 30 分钟”，**直接熔断，不再执行耗时的哈希比对**。
3.  **哈希比对 (Hash Verification)**：读取数据库中对应 User 的 `hashed_password`，使用 Argon2 或 Bcrypt 算法进行校验。
4.  **状态流转 (State Transition)**：
    * **失败**：密码错误。Redis 中失败计数器 +1。若达到阈值 3 次，可要求后续请求必须携带图形验证码；达到 5 次触发账号冻结。
    * **成功**：清除 Redis 中的失败计数器。
5.  **2FA 升维 (Step-up Authentication - 仅开启了双因素的用户)**：
    * 检测到 `User.is_2fa_enabled == True`。
    * 系统暂不下发正式 Token，而是下发一个 `MFA_Token`（有效期 5 分钟）。前端跳转至动态口令输入页。
    * 用户提交 6 位 Authenticator 动态码 + `MFA_Token`，后端基于 TOTP 算法验证通过后，才进入最终下发凭证环节。

### 工作流 D：会话续期与全局吊销流 (零信任生命周期)
此链路的架构目标是：**在实现前端“无感刷新”的同时，赋予用户和管理员随时斩断任何非法访问的能力（Session Revocation）。**

1.  **无感续期 (Silent Renewal)**：
    * 前端 Access Token 即将过期（或请求 API 时收到 401 状态码）。
    * 前端 Axios 拦截器挂起所有业务请求，静默向 `/auth/refresh` 发起请求。浏览器自动携带 HttpOnly 的 Refresh Token Cookie。
2.  **存活检验 (Liveness Check)**：
    * 后端解析 Refresh Token 获取 `session_id`。
    * **关键查询**：在 `active_sessions` 表中查找该 `session_id`。若查无此记录、或 `expires_at` 已过期、或 `is_revoked == True`，则拒绝刷新，返回 403，要求前端强制退回登录页。
3.  **续命操作 (Token Rotation)**：
    * 检验通过，后端生成新的 Access Token 返回给前端。前端恢复此前挂起的业务请求。
4.  **终端驱逐 (Remote Revocation)**：
    * 用户在“安全中心”看到异地登录的设备，点击“下线此设备”。
    * 后端将 `active_sessions` 表中对应的 `session_id` 的 `is_revoked` 字段置为 `True`，同时将该 `session_id` 写入 Redis 黑名单（用于处理 Access Token 的瞬时失效）。
    * 该设备在下一次（通常在几分钟内）请求业务接口或刷新 Token 时，将直接被踢出系统。修改密码操作将默认触发“驱逐其他所有终端”的动作。

### 工作流 E：安全邮箱绑定流 (防失联后备链路)
此链路的架构目标是：**建立高可靠的找回通道。即使由于换号、运营商问题导致手机号失效，用户依然能够凭借安全邮箱夺回账号控制权。**

1.  **意图发起**：用户处于登录状态，在“安全中心”点击“绑定安全邮箱”。
2.  **本人校验 (Identity Re-verification)**：为防止越权操作（如他人使用未锁屏的电脑），前端弹窗要求验证身份，输入当前账号的登录密码，或验证当前手机号的 SMS OTP。
3.  **投递探针 (Email Probe)**：
    * 校验通过后，用户输入拟绑定的安全邮箱地址。
    * 后端生成一个一次性的、包含邮箱地址和用户 UUID 的 `Verification_Token`（JWT，有效期 15 分钟）。
    * 将包含验证链接的邮件投递至 Celery 发送队列。
4.  **闭环确认 (Closure)**：
    * 用户登录邮箱，点击邮件内的激活链接（或输入邮件内包含的 6 位 OTP 验证码）。
    * 携带 `Verification_Token` 回调后端接口。后端校验 Token 有效性与合法性，更新 `users` 表的 `email` 字段，并将 `is_email_verified` 置为 `True`。

### 工作流 F：会话内修改密码流 (凭证轮换链路)
此链路的架构目标是：**提供安全的凭证更新机制，并在密码变更瞬间执行“零信任”阻断，清除旧凭证的潜在威胁。**

1.  **意图发起**：用户登录状态下，在“安全中心”选择“修改密码”。
2.  **三重鉴权**：用户需在表单中依次输入：旧密码、新密码、确认新密码。后端首先执行风控检查，随后验证旧密码的哈希。
3.  **密码策略拦截**：后端强制执行强密码检查（正则匹配：至少 8 位，包含大小写字母与数字等）。
4.  **落库与终端驱逐 (Atomic Update & Eviction)**：
    * 校验通过后，后端生成新密码的哈希并更新至数据库。
    * **关键安全动作**：在同一个数据库事务中，将该用户除了当前所在设备（`current_session_id`）以外的所有 `active_sessions` 标记为 `is_revoked = True`。
    * （可选）更为严格的策略是销毁包含当前设备在内的**所有**会话，并强制将用户踢回登录页重新认证。

### 工作流 G：忘记密码与账号找回流 (灾难恢复链路)
此链路的架构目标是：**在用户丧失当前凭证的情况下，通过多重 MFA 因子验证确权，安全地将系统访问权交还给真正的所有者。**

1.  **意图发起**：用户在登录界面点击“忘记密码”，跳转至账号找回页面，输入绑定的手机号。
2.  **验证通道选择 (Channel Selection)**：
    * 前端向后端查询该手机号关联的可用找回通道。
    * 后端返回部分脱敏的信息列表（如：手机号 `138****1234`，安全邮箱 `us***@gmail.com`）。
3.  **身份确认 (Identity Challenge)**：
    * **方式 1 (手机验证)**：用户选择短信验证，流程同免密登录。输入正确的 SMS OTP 后通过。
    * **方式 2 (邮箱验证 - Fallback)**：用户选择邮箱验证。后端生成一个携带时效性的 Magic Link 邮件。用户在邮箱中点击链接，回到平台并自动带上校验 Token。
4.  **下发重置令牌 (Reset Token Dispensation)**：
    * 无论走哪种通道，校验成功后，后端不直接登录，而是下发一个专属的临时 `Password_Reset_Token`（有效期 10 分钟，不可用于调用其他业务 API）。
5.  **凭证更新与清洗 (Update & Cleanse)**：
    * 用户在前端重置页面输入新密码，提交时带上 `Password_Reset_Token`。
    * 后端校验 Token 成功，哈希并更新密码。
    * **关键安全动作**：立即将该用户在 `active_sessions` 表中的所有会话记录批量置为作废（Revoked），将所有签发过的 Access Token 隐式失效。
    * 流程结束，引导用户使用新密码返回登录页重新建立全新的、安全的会话。

## 三、 渐进式实施路线图 (Progressive Implementation Roadmap)

这是非常务实且专业的工程策略。在拥有了极其庞大和复杂的生信 IDE 架构（包含沙箱、Celery、LangGraph、Vercel AI SDK）的基础上，进行这种牵一发而动全身的商业级身份验证（IAM）升级，**绝对不能搞“大爆炸”式的重构**。

基于你现有的代码库（尤其是现有的简单 `login` 页面、简陋的 `auth` 路由和 JWT 拦截器），我为你制定了一个**无痛、平滑、零停机的 5 阶段渐进式升级计划**。

我们的核心目标是：**在不影响现有任何生信业务流（Skill Forge、Chat、Data Center）的前提下，把底层的账号承载体系“偷梁换柱”，最后再开启风控和高阶认证。**

### 🚀 阶段 1：底层数据结构双向兼容 (Database & Schema Migration)

**当前痛点**：现有的 `User` 模型可能高度依赖 Email 或用户名，且没有为多设备会话（Session）和第三方绑定（OAuth）预留字段。

### 🔄 阶段 4：会话重构与双 Token 无感刷新 (Zero-Trust Session)

**当前痛点**：目前前端可能只在内存或 localStorage 里存了一个长期有效的 Access Token，存在极大的 XSS 窃取风险。
**本阶段目标**：部署“短命 Access Token + 长命 HttpOnly Refresh Token”，实现金融级会话安全。

**行动指南**：
1.  **后端 Token 签发改造**：
    * 修改 `/auth/login` 逻辑。生成 Access Token（15分钟），并生成一个随机字符串（Refresh Token）。
    * 将 Refresh Token、设备信息写入 `ActiveSession` 表。
    * 在 Response Header 中注入 `Set-Cookie: refresh_token=...; HttpOnly; Secure; SameSite=Lax`。
2.  **后端续期接口 (`/auth/refresh`)**：
    * 读取 Cookie 中的 `refresh_token`，查表验证其是否有效（`is_revoked == False`），有效则颁发新的 Access Token。
3.  **前端 Axios 拦截器大手术 (`src/lib/api.ts`)**：
    * 这是最难的一步。配置 Axios response 拦截器：当收到 `401 Unauthorized` 时，挂起当前请求流 -> 静默调用 `/auth/refresh` -> 拿到新 Access Token -> 重试之前挂起的请求。
4.  **前端用户中心改造 (`src/components/overlays/UserCenter/SecurityPanel.tsx`)**：
    * 读取 `ActiveSession` 表，渲染“在线设备管理”列表，并提供“踢人下线”的按钮（调用后端将对应 Session 置为 `is_revoked = True`）。

**验证标准**：将 Access Token 的过期时间故意调短为 1 分钟。在系统里疯狂点击各种功能，1 分钟后你会看到 Network 面板里自动发起了一个 `/refresh` 请求，业务完全没有中断（无感续期）。

### 2. 构建独立风控引擎 (`app/services/risk_control.py`)

保留原有的 Redis 频率限制与防暴力破解逻辑。该模块作为安全网关（L1/L2 防线），在调用阿里云接口前进行拦截。

```python
# autonome-backend/app/services/risk_control.py
from fastapi import HTTPException, status
from app.services.cache_service import cache
import logging

logger = logging.getLogger(__name__)

class RiskControlEngine:
    """
    基于 Redis 的分布式风控引擎，用于防范短信轰炸和暴力破解。
    支持参数化配置，可根据系统负载动态调整阈值。
    """
    # 默认风控参数系统
    SMS_LOCK_TTL = 60        # 发信冷却时间（秒）
    SMS_CODE_TTL = 300       # 验证码有效期（秒）
    SMS_DAILY_LIMIT = 10     # 单日单号发信上限
    LOGIN_MAX_FAILS = 5      # 最大允许密码错误次数
    LOGIN_LOCK_TTL = 1800    # 账号锁定时间（30分钟）

    @classmethod
    async def check_sms_rate_limit(cls, phone: str, ip: str):
        """
        短信发送前的风控拦截逻辑。
        
        Args:
            phone: 目标手机号
            ip: 请求来源 IP
        Raises:
            HTTPException: 触发频率限制时抛出 429 错误
        """
        # 1. 检查 60 秒发信冷却锁
        lock_key = f"risk:sms:lock:{phone}"
        if await cache.get(lock_key):
            raise HTTPException(
                status_code=status.HTTP_429_TOO_MANY_REQUESTS, 
                detail="发送过于频繁，请 60 秒后再试"
            )
            
        # 2. 检查单日发送上限
        daily_key = f"risk:sms:daily:{phone}"
        daily_count = await cache.get(daily_key)
        if daily_count and int(daily_count) >= cls.SMS_DAILY_LIMIT:
            logger.warning(f"[风控拦截] 手机号 {phone} 触发单日短信上限。IP: {ip}")
            raise HTTPException(
                status_code=status.HTTP_429_TOO_MANY_REQUESTS, 
                detail="该手机号今日发送次数已达上限"
            )

    @classmethod
    async def record_sms_sent(cls, phone: str, otp: str):
        """
        记录发信状态并写入验证码。
        
        Args:
            phone: 目标手机号
            otp: 6位验证码
        """
        code_key = f"auth:sms:code:{phone}"
        lock_key = f"risk:sms:lock:{phone}"
        daily_key = f"risk:sms:daily:{phone}"
        
        # 写入验证码，有效期 5 分钟
        await cache.set(code_key, otp, expire=cls.SMS_CODE_TTL)
        # 写入冷却锁，有效期 60 秒
        await cache.set(lock_key, "1", expire=cls.SMS_LOCK_TTL)
        
        # 单日计数器递增
        count = await cache.incr(daily_key)
        if count == 1:
            # 初始化单日计数器的过期时间为 24 小时 (86400秒)
            await cache.client.expire(daily_key, 86400)
            
    # ... 保留原有的 check_login_risk, record_login_failure 等密码防爆破逻辑 ...
```

```python
        self.access_key_secret = getattr(settings, "ALIYUN_ACCESS_KEY_SECRET", None)
        self.endpoint = "dysmsapi.aliyuncs.com"

    def _create_client(self) -> DysmsapiClient:
        """
        初始化并返回阿里云核心 Client。
        """
        config = open_api_models.Config(
            access_key_id=self.access_key_id,
            access_key_secret=self.access_key_secret
        )
        config.endpoint = self.endpoint
        return DysmsapiClient(config)

    async def send_verification_code_async(
        self, 
        phone_number: str, 
        code: str, 
        sign_name: Optional[str] = None, 
        template_code: Optional[str] = None
    ) -> bool:
        """
        异步发送验证码短信。
        
        Args:
            phone_number: 接收端手机号
            code: 验证码内容
            sign_name: 可选，短信签名。若为空则使用 settings 默认值。
            template_code: 可选，短信模板代码。若为空则使用 settings 默认值。
            
        Returns:
            bool: 发送是否成功
        """
        if not self.access_key_id or not self.access_key_secret:
            logger.error("[SMS Gateway] 阿里云 AccessKey 未配置，无法发送短信。")
            return False

        client = self._create_client()
        
        # 参数系统 fallback 逻辑
        actual_sign_name = sign_name or getattr(settings, "ALIYUN_SMS_SIGN_NAME", "Autonome")
        actual_template_code = template_code or getattr(settings, "ALIYUN_SMS_TEMPLATE_CODE", "")
        
        # 构建请求参数，阿里云要求模板参数为 JSON 字符串格式
        template_param = json.dumps({"code": code})
        
        send_sms_request = dysmsapi_models.SendSmsRequest(
            phone_numbers=phone_number,
            sign_name=actual_sign_name,
            template_code=actual_template_code,
            template_param=template_param
        )
        
        # 设置超时与运行参数
        runtime = util_models.RuntimeOptions(
            connect_timeout=5000, # 5秒连接超时
            read_timeout=10000    # 10秒读取超时
        )

        try:
            # 调用异步 API
            response = await client.send_sms_with_options_async(send_sms_request, runtime)
            
            # 阿里云的 Code 为 "OK" 表示成功
            if response.body.code == 'OK':
                logger.info(f"✅ [SMS Gateway] 阿里云短信发送成功: {phone_number}, BizId: {response.body.biz_id}")
                return True
            else:
                logger.error(f"❌ [SMS Gateway] 阿里云返回业务错误: {response.body.code} - {response.body.message}")
                return False

        except Exception as error:
            # 捕获并记录底层网络或 SDK 异常
            logger.error(f"❌ [SMS Gateway] 阿里云 SDK 执行异常: {str(error)}")
            return False
```

```python
    client_ip = request.client.host

         logger.warning(f"请求发信未携带 Captcha Token, IP: {client_ip}")

    bg_tasks.add_task(background_sms_task, phone, otp)
    
    return {"status": "success", "message": "验证码处理中"}
```

```python
    """
    知乎式主登录逻辑 (免密验证码登录 + 自动注册)
    """
    phone = payload.phone_number
    otp = payload.otp_code
    
    if not otp:

    await RiskControlEngine.check_login_risk(phone)

        # 记录失败次数，防暴力破解
        await RiskControlEngine.record_login_failure(phone)
        raise HTTPException(status_code=400, detail="验证码错误或已失效")
        
    # 2. 校验成功，**原子化立即销毁验证码**，并清空失败计数
    await cache.delete(code_key)
    await RiskControlEngine.clear_login_failure(phone)

    # 3. 身份解析：查找用户，若不存在则【静默注册】
    user = db.query(User).filter(User.phone_number == phone).first()
    is_new_user = False
    
    if not user:
        # 新用户自动入库
        import uuid
        user = User(
            id=uuid.uuid4(),
            phone_number=phone,
            # 临时生成唯一虚拟邮箱，后续引导绑定真实邮箱
            email=f"{phone}@autonome.local", 
            full_name=f"生信专家_{phone[-4:]}",
            is_active=True,
            is_email_verified=False
        )
        db.add(user)
        db.commit()
        db.refresh(user)
        is_new_user = True

    # 4. 下发凭证 (本阶段暂只下发 Access Token，阶段4再升级双 Token)
    access_token_expires = timedelta(minutes=settings.ACCESS_TOKEN_EXPIRE_MINUTES)
    access_token = create_access_token(
        subject=str(user.id), expires_delta=access_token_expires
    )
    
    return {
        "access_token": access_token,
        "token_type": "bearer",
        "is_new_user": is_new_user,

            "phone": user.phone_number,

        subject=str(user.id), expires_delta=access_token_expires

        "is_new_user": False,
```

### 🛠️ 第一步：后端核心安全算法补齐 (`app/core/security.py`)

我们需要在安全模块中新增生成和校验长效 Refresh Token 的方法。长效凭证绝不能明文存入数据库（防脱库），必须存其 Hash 值。

请在 `autonome-backend/app/core/security.py` 中追加以下内容：

```python
# autonome-backend/app/core/security.py (追加)
import secrets
import hashlib
from datetime import datetime, timedelta
from app.core.config import settings

def generate_refresh_token() -> str:
    """生成高熵的随机字符串作为 Refresh Token"""
    return secrets.token_urlsafe(64)

def hash_refresh_token(token: str) -> str:
    """对 Refresh Token 进行 SHA-256 摘要（用于存入数据库比对，防脱库泄露）"""
    return hashlib.sha256(token.encode()).hexdigest()

def get_refresh_token_expires_at() -> datetime:
    """计算 Refresh Token 的过期时间 (默认 7 天)"""
    # 假设你在 settings 中配置了 REFRESH_TOKEN_EXPIRE_DAYS = 7
    days = getattr(settings, "REFRESH_TOKEN_EXPIRE_DAYS", 7)
    return datetime.utcnow() + timedelta(days=days)
```

```python
    db.commit()
```

### 🌐 第三步：前端网络拦截器改造（实现“无感续期”）

这是前端难度最大的一步。在 `autonome-studio/src/lib/api.ts` 中，我们需要封装一个高级的 `fetch` 包装器。当检测到后端返回 401（Access Token 过期）时，**拦截当前请求，静默调用 `/api/v1/auth/refresh` 换取新 Token，然后重试失败的请求。**

完全替换或重构你 `src/lib/api.ts` 中的网络请求逻辑：

```typescript
// autonome-studio/src/lib/api.ts
import { useAuthStore } from '@/store/useAuthStore';

export const BASE_URL = process.env.NEXT_PUBLIC_API_URL || 'http://localhost:8000';

// 并发刷新锁（防止多个 API 同时返回 401 时发起多个 refresh 请求）
let isRefreshing = false;
let failedQueue: Array<{ resolve: (token: string) => void; reject: (err: any) => void }> = [];

const processQueue = (error: any, token: string | null = null) => {
  failedQueue.forEach(prom => {
    if (error) {
      prom.reject(error);
    } else {
      prom.resolve(token as string);
    }
  });
  failedQueue = [];
};

/**
 * 带有无感刷新能力的自定义 Fetch 包装器
 */
export async function fetchWithAuth(endpoint: string, options: RequestInit = {}) {
  const getAccessToken = () => useAuthStore.getState().token;
  const setAccessToken = useAuthStore.getState().setToken;

  let token = getAccessToken();
  
  const headers = new Headers(options.headers);
  if (token) {
    headers.set('Authorization', `Bearer ${token}`);
  }
  
  // 注入跨域 Cookie 携带（核心，为了带上 HttpOnly Cookie）
  const config: RequestInit = {
    ...options,
    headers,
    credentials: 'include' 
  };

  let response = await fetch(`${BASE_URL}${endpoint}`, config);

  // 如果状态是 401，说明 Access Token 过期了，准备执行刷新流
  if (response.status === 401) {
    if (!isRefreshing) {
      isRefreshing = true;
      try {
        // 调用后端 refresh 接口，浏览器会自动带上 HttpOnly 的 refresh_token cookie
        const refreshRes = await fetch(`${BASE_URL}/api/v1/auth/refresh`, {
          method: 'POST',
          credentials: 'include' 
        });

        if (refreshRes.ok) {
          const data = await refreshRes.json();
          const newToken = data.access_token;
          
          // 更新 Zustand store
          setAccessToken(newToken);
          
          // 放行等待队列中的请求
          processQueue(null, newToken);
          
          // 重试当前失败的请求
          headers.set('Authorization', `Bearer ${newToken}`);
          response = await fetch(`${BASE_URL}${endpoint}`, { ...config, headers });
        } else {
          // Refresh Token 也失效了 (例如被踢下线)，强制退出
          throw new Error('Session Expired');
        }
      } catch (err) {
        processQueue(err, null);
        // 清理本地状态并重定向到登录页
        setAccessToken(null);
        window.location.href = '/login';
      } finally {
        isRefreshing = false;
      }
    } else {
      // 正在刷新中，其他并发的 401 请求进入队列等待
      return new Promise<Response>((resolve, reject) => {
        failedQueue.push({
          resolve: (newToken: string) => {
            headers.set('Authorization', `Bearer ${newToken}`);
            fetch(`${BASE_URL}${endpoint}`, { ...config, headers }).then(resolve).catch(reject);
          },
          reject: (err: any) => reject(err)
        });
      });
    }
  }

  return response;
}
```

*注意：此后你的前端组件中请求后端接口时，不再使用原生的 `fetch`，全部替换为 `fetchWithAuth('/api/v1/...')`。*

```python
from fastapi import Query
import httpx

@router.get("/github/login")
async def github_login():
    # 生成随机 state，防 CSRF，存入 Redis
    state = secrets.token_hex(16)
    await cache.set(f"oauth_state:{state}", "pending", expire=600)
    
    # 重定向到 GitHub 授权页
    github_auth_url = f"https://github.com/login/oauth/authorize?client_id={settings.GITHUB_CLIENT_ID}&state={state}"
    return {"url": github_auth_url}

@router.get("/github/callback")
async def github_callback(code: str, state: str, db: Session = Depends(get_db)):
    # 1. 校验 state 防伪造
    if not await cache.get(f"oauth_state:{state}"):
        raise HTTPException(status_code=400, detail="Invalid state")
    
    # 2. 用 code 换取 token 和用户信息 (使用 httpx 异步请求)
    async with httpx.AsyncClient() as client:
        # (此处省略换取 Access Token 和 UserInfo 的标准逻辑)
        user_info = await get_github_user_info(code) 
    
    github_id = str(user_info['id'])
    
    # 3. 匹配映射
    oauth_account = db.query(OAuthAccount).filter(
        OAuthAccount.provider == "github",
        OAuthAccount.provider_account_id == github_id
    ).first()
    
    if oauth_account:
        # 已绑定，直接下发双 Token
        return issue_tokens(oauth_account.user)
    else:
        # [关键分支]: 未绑定，不创建 User，下发受限 Bind_Token
        bind_token = create_bind_token(github_id=github_id, email=user_info.get('email'))

            "bind_token": bind_token,
```

以下是实现微信扫码登录的完整技术指导：

### 一、 前置条件与准备
1.  **微信开放平台注册**：申请并审核通过【网站应用】，获得 `AppID` 和 `AppSecret`。
2.  **配置回调域名**：在开放平台后台配置回调域，例如 `https://api.autonome.com/auth/wechat/callback`。
3.  **启用授权作用域**：确保应用具备 `snsapi_login` 权限。

### 二、 核心实现工作流 (OAuth 2.0 授权码模式)

流程分为三步：前端发起请求 -> 后端获取用户信息 -> 完成绑定与身份映射。

#### 1. 前端：发起扫码请求
在登录页点击“微信登录”按钮时，将用户重定向到微信登录页。

```typescript
// autonome-studio/src/app/login/page.tsx
const handleWechatLogin = () => {
  const appid = 'YOUR_WECHAT_APP_ID';
  const redirectUri = encodeURIComponent('https://api.autonome.com/auth/wechat/callback');
  const state = Math.random().toString(36).substring(7); // 防 CSRF
  // 将 state 存入 Redis，用于回调校验
  
  const url = `https://open.weixin.qq.com/connect/qrconnect?appid=${appid}&redirect_uri=${redirectUri}&response_type=code&scope=snsapi_login&state=${state}#wechat_redirect`;
  window.location.href = url;
};
```

#### 2. 后端：处理回调并交换凭证 (`app/api/routes/auth.py`)

后端需要通过 `code` 换取 `access_token`，再获取微信用户的 `unionid`（唯一标识）。

```python
# autonome-backend/app/api/routes/auth.py

import httpx

@router.get("/wechat/callback")
async def wechat_callback(code: str, state: str, db: Session = Depends(get_db)):
    # 1. 校验 state (从 Redis 读取并对比)
    
    # 2. 换取 Access Token
    async with httpx.AsyncClient() as client:
        token_url = f"https://api.weixin.qq.com/sns/oauth2/access_token?appid={settings.WECHAT_APP_ID}&secret={settings.WECHAT_APP_SECRET}&code={code}&grant_type=authorization_code"
        token_resp = await client.get(token_url)
        token_data = token_resp.json()
        
        # 3. 获取用户基本信息 (包含 unionid)
        user_url = f"https://api.weixin.qq.com/sns/userinfo?access_token={token_data['access_token']}&openid={token_data['openid']}"
        user_info = await client.get(user_url).json()
        
    unionid = user_info['unionid']
    
    # 4. 业务匹配：查找是否已绑定手机号
    oauth_acc = db.query(OAuthAccount).filter_by(provider="wechat", provider_account_id=unionid).first()
    
    if oauth_acc:
        # 已绑定，直接登录，下发 JWT (复用之前定义的 issue_tokens 逻辑)
        return issue_tokens(oauth_acc.user)
    else:
        # [关键闭环]: 未绑定，返回 Bind_Token 强制跳转前端绑定手机号
        bind_token = create_bind_token(wechat_unionid=unionid)
        return {"status": "requires_binding", "bind_token": bind_token}
```

### 四、 关键的技术挑战与打磨 (商业级注意事项)

#### 1. 账号唯一性冲突处理 (UnionID vs OpenID)
* **UnionID 是关键**：微信同一个用户在同一个开放平台下的不同应用（公众号、小程序、网站）的 `OpenID` 是不同的，但 `UnionID` 是唯一的。**必须使用 UnionID 作为数据库的唯一绑定 ID**，否则用户换个入口登录就会导致账号分裂。

#### 2. 强制绑定手机号 (与之前阶段的闭环联动)
既然您确定采用“一律绑定手机号”的策略，微信登录的回调必须触发我们在【阶段 5】设计的强制弹窗：
* **前端状态机**：如果后端返回 `requires_binding`，前端路由必须从 `dashboard` 切换到 `bind_phone` 模态框。
* **安全性**：绑定手机号时，必须再次校验该手机号是否已被其他微信绑定过（防账号覆盖冲突）。

#### 3. 关于微信网页授权的适配
* **二维码嵌入**：为了获得更好的体验，可以使用“微信登录”插件的 `JS SDK` 将登录二维码直接嵌入在您的登录页内，而不是跳转到微信官网。
    ```html
    <script src="https://res.wx.qq.com/connect/zh_CN/htmledition/js/wxLogin.js"></script>
    <script>
      var obj = new WxLogin({
        id:"login_container", 
        appid: "wx_appid", 
        scope: "snsapi_login", 
        redirect_uri: "your_callback_url"
      });
    </script>
    ```
